# Аудит Casting Autopilot: доступ к источникам, безопасность, надёжность и качество

**Дата:** 31.10.2026  
**Исследованная версия:** `2bb1a38270f4dd77d0ef6d27d3f7edbe8a83b141` (PR #1, `feat/selected-casting-sources-ai-safety`)  
**Режим:** только чтение действующего проекта; ни одной авторизации пользовательского Telegram, включения экспериментального сборщика или изменений производства.  
**Решение:** **NO-GO** для подключения основного Telegram-аккаунта в облако. **GO** для изолированных тестов на синтетических сообщениях и для пилота с явно разрешённым источником.

## 2. Безопасность, права и приватность

**Блокирующие риски (P0):**
- Telegram API Terms п. 2.1 требует собственный `api_id` для стороннего клиентского приложения: https://core.telegram.org/api/terms. Подключение через внутренние вызовы Telegram Web не отменяет автоматически условий платформы.
- Telegram Bot Developer Terms, п. 4.3, запрещает сбор несущественных данных и определённый скрейпинг больших наборов/AI-продуктов: https://telegram.org/tos/bot-developers.
- Content Licensing Terms ограничивает использование опубликованного контента и запрещает сбор для обучения/разработки/развёртывания ИИ без установленного разрешения/исключения: https://telegram.org/tos/content-licensing. Нельзя считать опубликованное в открытой группе автоматически лицензированным для массовой индексации или передачи сторонней модели.
- Полноценная облачная сессия содержит права аккаунта. При краже профиля браузера возможен доступ к личной переписке. Пароль, `tdata`, сессия, QR-код и отладочный порт Chromium не должны быть публичными.
- `app/cloud_web_reader.py` экспериментальный и не входит в текущий запуск. Нельзя просить администратора авторизоваться, пока нет безопасного изолированного входа и процедуры отзыва сессии.

**Высокие риски (P1):**
- В базе существуют профили (город, возраст, рост, пол), тексты сообщений, история доставок и оценки. В действующем Bot API нет пользовательской команды полного удаления данных (`/delete` или аналогичной), а срок хранения не ограничен явно.
- `app/bot_http.py` содержит дефект PNG-подписи: сравнение с `b"\\x89PNG\\r\\n\\x1a\\n"` использует экранированную последовательность вместо реального бинарного заголовка PNG. Независимый локальный тест: реальный заголовок `89504e470d0a1a0a` отвергается текущей проверкой.
- Передача QR через обычное сообщение Telegram потенциально сохраняет одноразовый доступ в истории чата. Нужны анализ модели угроз, короткий срок жизни, подтверждение владельцем и отсутствие хранения изображений.
- Защищённые группы и сообщения с запретом пересылки требуют отдельного соблюдения правил контента: https://core.telegram.org/api/content-protection.

**Рекомендация:** не собирать сообщения чужих групп для обучения модели; до явного правового основания не отправлять содержимое сторонним ИИ-сервисам. Для пилота использовать разрешённый партнёрский источник, минимальное хранение, правила удаления и исключение личных переписок.

## 3. Надёжность и разрыв между тестами и работой

**Подтверждено по GitHub/Railway:**
- Railway `web`: `SUCCESS`, один экземпляр, постоянный том; в текущем журнале `Bot API started: no user session used` и `Public scanning enabled: 3 selected sources`.
- PR #1 содержит `app/cloud_web_reader.py`, но `app/bot_runtime.py` не вызывает `CloudWebReader` и не обрабатывает `/authorization`. Поэтому введённая пользователем команда не могла показать QR.
- В `requirements.txt` отсутствует `playwright`, а в `Dockerfile` не устанавливается Chromium. Значит, запустить облачный прототип в текущем образе нельзя.
- GitHub CI запускает `compileall` и `unittest`, но не реальный браузер, не вход в Telegram, не чтение реальных групп и не доставку на реальный аккаунт.
- Публичный сканер ограничивает глубину истории доступными веб-публикациями. Объявления могут быть пропущены при высокой частоте сообщений даже в заданном окне 48 часов.
- Курсовые и доставочные идентификаторы сохраняются в SQLite, но это не подтверждает полноту получения исходных сообщений.

**Обязательные тесты для выхода из NO-GO:**
1. Без аккаунта проверить парсер и обработчик на искусственных примерах: обычное объявление, 2 роли, истёкший срок, курс, пустое сообщение, повтор поста.
2. На отдельной копии базы проверить миграцию, повторную доставку, сохранение курсора, сбой между получением и фиксацией, блокировку отправки, ограничение 429.
3. Для веб-клиента отдельно проверить авторизацию, разлогин, двухэтапный пароль, смену версии Telegram Web, закрытие вкладки, получение `FLOOD_WAIT`, отсутствие доступа к неразрешённым группам.
4. Только при наличии разрешения владельца конкретного источника провести испытание одной реальной публикации; документировать факт получения, профиль совпадения, отправку и отсутствие повтора.
5. Отдельно проверить возможность **отозвать облачную сессию** через Telegram → Настройки → Устройства, без утечки данных.

## 4. Качество подбора и измеримость

Рабочая фильтрация использует словари и регулярные выражения (`app/casting_quality.py`, `app/matcher.py`), а не подключённую модель ИИ. Это должно быть явно указано пользователям.

Перед оценкой «обучается» необходимы:
- 50–100 **разрешённых или синтетических** контрольных объявлений, с заведомыми правильными метками «кастинг/не кастинг», городом, полом, возрастом, ростом, сроком и несколькими ролями;
- раздельный подсчёт **полученных источником**, **отброшенных фильтром**, **совпавших с профилем**, **поставленных в очередь**, **доставленных**;
- показатели точности: доля правильных отправлений (precision), полнота обнаружения среди доступных разрешённых объявлений (recall), процент повторов и задержка доставки;
- разбор отказов и отзывов `👍/👎`, но без автоматического обучения на чужих текстах.

**Проблема честности статусов:** команда `/castings` сообщает об отсутствии подходящих публикаций даже если нет доступа к источникам. Следует отделить «источник недоступен», «посты получены, совпадений нет» и «подходящие посты доставлены».

## Решение по архитектуре

**Рекомендуемый безопасный порядок:**
1. **Сейчас:** сохранить Bot API, профиль, очередь, дедупликацию; не включать Telethon/Telegram Web и не просить QR у основного аккаунта.
2. **Первый подтверждаемый поток:** партнёрский публичный канал/группа с разрешением администратора на подключение бота, либо собственный разрешённый источник. Проверить одно реальное объявление от начала до конца.
3. **Далее:** добавлять только разрешённые публичные RSS/веб-источники или лицензированные фиды. Где источник недоступен, честно показывать отсутствие доступа.
4. **Экспериментальная ветка:** Telegram Web исследовать только после отдельной оценки прав, согласия, безопасности и процедуры отзыва сессии; не объединять автоматически с производством.
5. **Перед расширением:** ограничение хранения, удаление данных, изолированное тестирование и прозрачная статистика.

| Unit-тесты кода бота в GitHub | ДА |

**Вывод:** действующий бот технически жизнеспособен как интерфейс подписок и доставки, но источник сообщений для выбранных чужих групп не подтверждён. Без этого нельзя честно утверждать, что работает автономный мониторинг кастингов. Дальнейший шаг — проверка одного разрешённого источника без облачной сессии личного аккаунта.
